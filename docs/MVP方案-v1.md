# 立体婚礼邀请函 MVP 方案 v1

日期：2026-11-04。用途：指导首款样品、可售版本和工作室交付。

已确认：产品用于新人向亲友发送电子婚礼邀请；工作室定制模式；形态参考 R01 + R17 / R02；本轮选图 P01、P04、P05、P08、P09、P11、P12、P24。

本文提出的主题、章节、功能边界及指标属于方案建议。参考选择已经明确，原创美术和运行效果仍需实际样品验收。

## 1. 首款产品

暂名「花园来信」。一册可以打开、合拢、转动和逐章翻阅的婚礼纸艺书，包含一个封面、四个立体章节。新人提供文字和最多六张照片，工作室完成构图、裁剪、校对和发布，交付一个专属链接与一张分享封面。

宾客打开后立即知道谁结婚、哪一天；点开书即可看到场地、花园和新人逐层立起。愿意细看的人可以读故事、翻照片；查婚礼时间地点的人可以直接进入婚礼信息。

首版验证三个问题：这本书是否值得新人分享；亲友是否顺利找到婚礼信息；第二份订单是否能复用设计和代码。

### 美术规则

- 建议配色：暖米白 `#F4EBDD`、森林绿 `#234536`、鼠尾草绿 `#7C8D73`、少量暖玫瑰 `#BD7770`、旧金 `#AF9564`。此配色待首张原创样稿检验。
- 主体有不规则切纸轮廓、轻微纸纹、可见纸边和柔和接触阴影。用一处明确主光建立层次。
- 新人采用自然比例的插画剪影或半写实纸片；首版预设姿态，照片保留为照片。精确人物肖像属于单独定制工作。
- 每章先规划 5–7 个景深层、一个明确主体、一个主要动作；细节放在花叶、建筑窗格和边缘。先在手机尺寸判断，再增加细节。
- 中文姓名与日期是主要信息；英文可作短装饰。正文使用清楚可读的字体，字体及素材随项目本地托管。
- 参考图仅供设计对照。正式作品制作原创分层资产，记录所用字体、音乐及素材来源。

## 3. 书体与操作

沿用 R02 / R17 对应的环形立体书思路：围绕书脊展开四个扇区，每个扇区是一幕纸剧场，浏览时镜头对准当前扇区。

首版的「翻页」定义为沿书脊转向相邻章节，纸页和场景跟随书体变化。独立的整页弯曲翻书机制放到后续评估。这样保留开合、旋转、逐章翻阅，同时只需维护一套书体运动。

- 点「打开请柬」：封面展开，书页扇开，建筑、花叶和人物按固定轴立起。首次展开目标 2–3 秒，可跳过至稳定状态。
- 点上一章 / 下一章或轻扫场景：切换一个扇区并吸附到正面视角，目标 0.8–1.2 秒。
- 在场景内拖动：以章节切换为主；细微左右视角变化展示纸层，限制俯仰，避免看到不可阅读的背面。
- 点「合上」：可见纸片收拢、页面收回、封面合拢。实现几种可复用折轴，不在首版做任意纸机关物理求解。
- 每章提供一个可选动作；操作失败或用户不点击，仍能读完邀请信息。
- 底部一直可进入「婚礼信息」。照片查看、信息面板打开时，暂停书体手势，避免误翻页。

状态：封面 → 开书中 → 第 1–4 章 → 收书中 → 封面。动画中只接收一个待执行的章节目标；弹窗关闭回到原章。故障时进入同章的静态版本。

## 5. 首版功能边界

### 可销售版本必须完成

| 功能 | 明确范围 |
| --- | --- |
| 立体书 | 1 套主题、封面 + 4 章、开合、章节旋转、前后翻阅、有限视角调整 |
| 内容替换 | 两位新人姓名、日期时间、场地名、地址、邀请短句、最多三个故事节点、最多四项流程 |
| 照片 | 0–6 张，上传、旋转纠正、裁剪、排序、删除、大图查看。零照片时使用插画版回忆页 |
| 场地表现 | 首款样品制作一栋原创示例建筑；普通订单使用通用花园，准确还原真实场地列为加项 |
| 实用信息 | 独立信息面板、地图链接、复制地址、下载日历文件。地图或日历唤起失败仍能查看信息 |
| 音乐 | 一首可使用的背景音乐、开关、播放失败反馈；默认静音，由宾客主动开启 |
| 分享 | 稳定作品链接、专门排版的分享封面及方形缩略图裁切、复制链接、保存封面 |
| 手机与微信 | 手机竖屏优先、桌面适配、iOS / Android 微信实际打开及转发检查 |
| 降级 | 完整 3D、简化 3D、静态章节；减少动画偏好可用；婚礼信息始终可读 |
| 访问 | 管理员草稿；发布后仅凭链接访问；可选访问码；撤回、到期、更新和恢复上一发布版本 |
| 工作室工具 | 登录、复制模板、表单填内容、上传裁剪、预览、发布、撤回；编辑草稿不影响已发布内容 |

内容限制作为表单验证：姓名每人建议不超过 12 个字符；邀请短句不超过 60 字；每个故事正文不超过 80 字；地址不超过 120 字。超限提示改写或人工处理，关键地址不截断。照片支持 JPEG / PNG / WebP，HEIC 提示转换或由工作室处理；建议单图上传限 20 MB，发布时生成压缩派生图。

### 后续范围

首版交付集中在邀请体验。自动收款、买家自助搭场景、多主题商城、自动生成相似人物、自由 360° 镜头、视频上传暂放后续。

RSVP 出席回执建议作为首个增量功能：现有联系方式可完成首批邀约；若首批客户明确需要统计人数，再增加「姓名、是否出席、人数、可选留言」和工作室导出。首版不展示没有接通的回执按钮。宝宝、宠物主题只保留内容模型和模板接口。

## 6. 美术怎样做成可复用资产

首轮先完成封面和第一章。交付物包括正面展开图、斜侧面图、开到一半的姿态图、手机尺寸构图及实际分层文件。

每个纸片需要：透明图像、实际轮廓、前后位置、折叠轴、旋转范围、支撑关系。建筑和新人为独立主体，前景草丛、树木、花叶、纸框可复用。短句及姓名由程序排版，不把客户文字烘焙进不可替换的底图。

制作顺序：统一画风样稿 → 分离前中后景 → 修复透明边缘 → 标注折轴和纸边 → 导入场景 → 调整阴影与遮挡 → 在手机上看动作。AI 可辅助构思及生成插画素材，交付文件仍需人工校色、分层和构图检查。

预计整书约 30–45 个可复用纸艺部件，外加一组照片框和文字版式。数量用于工作量估算；以清楚构图和性能测试决定实际保留量。

## 7. 技术架构

建议使用 TypeScript + React；网页路由、内容 API 和管理界面放在一个 Next.js 应用中。立体部分以 Three.js / React Three Fiber 实现，HTML 负责姓名日期、信息面板和操作控件。只在浏览器加载 3D 模块。

```text
工作室表单 → 草稿数据 + 原始照片 → 裁剪/压缩 → 手机预览
                                           ↓ 发布版本
宾客专属链接 → 访问校验 → 作品内容 → 3D 书体 / 静态章节
                                  → 婚礼信息、封面、日历
```

| 模块 | 职责 |
| --- | --- |
| BookEngine | 封面、书脊、四扇区、相机、开合及章节状态 |
| PaperScene | 带纸边的裁切图形、折轴、层次、阴影；相邻纸层避免深度冲突 |
| GardenTemplate | 四章布局、颜色、装饰和可替换内容槽位 |
| InvitationContent | 同一份姓名、时间、地点、文案，供 3D 标签、HTML 和日历使用 |
| Studio | 录入、照片裁剪、预览、发布及撤回 |
| Publication | 稳定链接、版本、访问权限、到期、分享图 |

3D 用真实书体与薄片几何，插画作为纹理；重要轮廓裁切成网格，小叶片可使用带透明通道的贴图。透明排序、两面显示及斜视纸边是第一章就要解决的问题。

开合与章节动画使用统一时间线控制；折轴必须随书页联动，避免纸片穿入书面。停下后按需渲染，动画或操作时请求下一帧；按实测降低像素比及阴影。[React Three Fiber 官方性能文档](https://r3f.docs.pmnd.rs/advanced/scaling-performance)

数据使用一个关系型数据库，照片与分享图放对象存储。最少需要作品、发布版本、素材和管理员四类记录。数据包含 `schemaVersion`、`templateId`、`templateVersion`、`eventType`、日期时间与时区、照片裁剪参数、发布状态、访问模式及到期时间。后续新增主题可复用引擎和出版流程。

受访问码保护的作品在服务端校验；照片与内容同样受控。访问码不写进公开配置或前端代码。无访问码作品适合宾客凭链接查看，持有者可以转发；`noindex` 仅用于减少索引，不承担授权功能。

## 8. 分享、音乐和降级

### 分享

所有作品提供可直接访问的 HTTPS 链接和独立封面图。网页输出对应的标题、描述和图片元数据；受保护作品默认使用不含私人照片的封面，公开字段由新人确认。

微信自定义聊天卡片单列为上线验证项：实施时核验现有账号的接口权限、域名配置和服务端签名，在收件人手机观察最终标题与图片。本轮微信官方文档未成功读取，因此不把具体账号可用性视为已确认。普通链接可访问、封面可保存和微信自定义卡片应分别验收；账号条件尚未具备时，先交付链接与封面，销售说明中不承诺已经支持自定义卡片。

### 音乐

默认静音，提供清楚的开启按钮；用户手势内发起播放，失败则保留播放入口。浏览器可能限制有声自动播放，需处理 `play()` 拒绝。[MDN 媒体自动播放说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

### 性能目标

以下是待验证的工程预算，均非已测结果。

- 信息和封面优先加载，3D 代码随后加载；首章可操作所需的传输资源目标不超过 3 MB，整书必要资源目标不超过 8 MB，后续照片及音乐按需加载。另记录解码纹理占用，文件小不代表显存占用低。
- 以冷缓存、10 Mbps 下行、100 ms 延迟为参考条件，目标 2 秒内显示姓名日期，5 秒内首章可操作；记录实际设备与网络，依据结果调整资产预算。
- 已选定的中档测试手机在开合和转章时，平均帧率目标至少 30 fps，记录低帧和长卡顿；静止场景不持续刷新。
- 简化模式减少阴影、限制像素比和装饰；WebGL 不可用、上下文丢失或持续卡顿时转入静态章节。手动「简洁查看」随时可用。
- 降级保留同一套插画、姓名、照片、地点及操作；数据从同一作品版本读取。超时显示重试及直接查看信息入口。

## 9. 工作室交付

客户提交姓名、婚礼时间地点、0–6 张照片、故事短句、是否设置访问码。标准服务复用主题、机关与版式；逐单调整排版、照片构图及信息。人物肖像、指定场地重绘或全新机关另作定制评估。

流程：资料齐全 → 复制模板 → 编辑与裁剪 → 手机预览 → 新人核对姓名日期地址 → 发布 → 交付链接与封面。变更先进入草稿，发布后原链接读取新版本，出现问题可回到上一版。

建议先以两轮文字/照片修改、明确的在线维护期限作为测试服务边界。初步可用 12 个月，承诺前先核算托管维护成本。暂不沿用旧报告中的测试价格；完成样品后，用实际美术及交付工时决定报价。

记录每单制作时间、修改时间、重绘时间和故障；模板内容替换目标控制在 30–60 分钟内，不包含客户等待、单独重绘及修改轮次。

资源估算：A 约 3–5 个工作日，B 约 3–5 日，C 约 5–7 日，D 约 4–6 日，E 约 3–5 日。合计约 18–28 个投入工作日，按全职投入约 4–6 周；美术迭代、账号准备和等待反馈会影响日历工期。完成 B 后依据实际耗时重估。

开发优先级：先投入封面、第一章和手机表现，再展开其余章节及工作室功能。

## 11. 验收

**视觉**：正面、斜侧、开到一半均可看见合理纸层；建筑和人物有共同笔触与光线；连续开合 10 次无穿插闪烁、残留物或姿态错乱。用户对实际原创样品的接受单独记录，程序通过不代替美术验收。

**邀请任务**：请 5 位首次使用者从链接进入，在无需讲解的情况下找到日期、时间和完整地点，目标至少 4 人在 10 秒内完成。所有人都能找到直接信息入口。该目标用于试验，并非既有结果。

**内容变化**：两份示例作品分别使用长短姓名、不同日期、横竖照片，另测零照片和六照片；内容更新不改源码，不影响另一份作品，关键文本不被截断。

**设备**：记录至少一台 iPhone、一台中档 Android 的机型、系统和微信版本，测试微信打开/转发/重开；另测 Safari、Chrome；覆盖约 360、390、430 CSS px 的竖屏布局。桌面模拟不替代手机记录。

**异常**：测试弱网、照片失败、音乐拒播、WebGL 初始化失败及上下文丢失；可以继续读信息，失败操作可重试。快速点下一章、切后台再返回不会卡在半开状态。

**权限与发布**：草稿不能公开读取；访问码同时保护内容和照片；撤回停止新请求，说明已下载内容无法远程收回；版本回滚可用。分享封面与作品版本一致。

**小规模验证**：先让 3–5 对目标新人试用样品，再尝试 5 笔付费试单。记录购买原因、拒绝原因和每单工时；付款与完成交付比点赞更能验证可售性。此为实验设计，不是销售预测。
